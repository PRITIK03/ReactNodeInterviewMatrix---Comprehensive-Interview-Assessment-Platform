# Security assessment and remediation plan

This document records the original assessment. The [controlled demo release guide](../release.md) describes the implemented services and current verification gates.

Status: Phase 0 assessment. This document contains no credential values or
candidate records.

## Current risk posture

The current application is a local prototype and must not be treated as a
public multi-tenant service. The highest risks are identity, authorization,
assessment integrity, file path construction, unsafe rendering, and historical
secret exposure.

| ID | Risk | Severity | Current evidence | Remediation |
|---|---|---:|---|---|
| S-01 | Fake authentication and no authorization | Critical | `Login.jsx` accepts any nonempty values; API has no auth dependency | Implement password hashing, sessions/tokens, route guards, and role checks |
| S-02 | Unauthenticated profile access | High | `/api/profile` accepts arbitrary username | Bind queries to authenticated subject and organization |
| S-03 | Path traversal | High | `data_loader.py` builds paths from company input | Enum allowlists plus resolved-path containment |
| S-04 | Client-controlled aptitude scoring | High | Submit request includes questions and answers | Server-owned attempt/question snapshots |
| S-05 | Unsafe AI HTML rendering | High | `Result.jsx` uses `dangerouslySetInnerHTML` | Safe markdown renderer or strict sanitizer |
| S-06 | Historical exposed credentials | Critical operational risk | Sensitive environment and local data existed in history | Revoke, rotate, then coordinate history remediation |
| S-07 | Plaintext account data | High | Historical JSON account store used plaintext values | Delete from source/history, migrate to hashed identity store |
| S-08 | Arbitrary code execution risk | Critical if enabled incorrectly | No runner currently exists; future feature requires isolation | Separate sandbox with no app credentials/network |
| S-09 | Resume upload risks | High for planned feature | Upload pipeline does not yet exist | Private object storage, scanning, quotas, parser isolation |
| S-10 | Tenant isolation | Critical for planned recruiter product | No tenant model exists | Organization-scoped authorization and object/query isolation |

## Historical credentials and data

The earlier repository history included a real environment credential type,
plaintext account data, candidate profile data, generated bytecode, and local
metadata. Values are intentionally not reproduced here.

Safe procedure:

1. Revoke every historical API key and reset any reused passwords.
2. Generate replacement credentials in the provider and deployment secret store.
3. Preserve a forensic copy only if required for incident handling, with access
   restricted and documented.
4. Decide which refs and forks are in scope for history removal.
5. Use `git-filter-repo` or an equivalent reviewed tool in a fresh mirror clone.
6. Verify the rewritten repository with secret scanning and object searches.
7. Coordinate with collaborators before any force push.
8. Require clean reclones or carefully documented rebase steps afterward.
9. Enable GitHub secret scanning and push protection.

Do not rewrite history automatically in this phase. A later history rewrite is
an operational action requiring explicit approval, a backup, and coordination.

## Authentication and authorization target

- Passwords use a modern password hashing function such as Argon2id.
- Sessions use secure, HttpOnly, SameSite cookies or short-lived access tokens
  with refresh rotation.
- Recruiter routes require organization membership and role permissions.
- Candidate routes require candidate ownership or a signed assignment context.
- Every object lookup includes organization/subject scope.
- Logout revokes the session server-side.
- Password reset and invitation tokens are single-use and expire.
- Login, invitation, and evaluation endpoints are rate-limited.

## Input and file security

### Path traversal

Company, level, question, and file identifiers must be allowlisted. Never use a
raw client string as a filesystem path. Public question content should be read
through a repository that maps a known enum to a known file or database record.

### Assessment integrity

The server creates an attempt and snapshots the published assessment version.
The client sends answer values only. The server owns answer keys, timing,
question identity, scoring, finalization, and result publication.

### AI HTML

AI output is untrusted. Store structured fields and render text. If markdown is
needed, use an allowlist that removes scripts, event handlers, unsafe URLs, raw
HTML, and embedded objects.

### Code execution

The runner must have:

- A non-root user.
- Ephemeral filesystem.
- CPU, memory, process, output, and wall-clock limits.
- No host mounts or application credentials.
- Default-deny network policy.
- Language-specific images pinned by digest.
- Job-level cancellation and cleanup.
- Separate worker pool and monitoring.

### Resume uploads

- Accept only a small allowlist of document types.
- Enforce size, page, and decompression limits.
- Validate content by magic bytes, not extension alone.
- Scan before parsing.
- Store privately with per-tenant object keys.
- Parse in a restricted worker.
- Strip active content where applicable.
- Never expose provider credentials to parsing code.
- Record consent, retention, and deletion status.

## Tenant isolation

Tenant context must be established from the authenticated principal, never from
a request body or query parameter. Repository methods should require tenant ID;
tests should attempt cross-tenant reads, writes, object access, analytics, and
background-job callbacks.

## Security verification gates

Before production exposure:

- Automated auth and authorization tests.
- Path traversal and payload-boundary tests.
- Secret scanning in CI and pre-push protection.
- Dependency and container scanning.
- Upload malware and parser-fuzz tests.
- Sandbox escape review.
- XSS and unsafe URL tests.
- Tenant-isolation integration tests.
- Backup restore test.
- Incident response and credential rotation runbook.
